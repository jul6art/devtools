# ADR-0023 — Gate : Claude ne peut pas déclarer la tâche finie tant qu'elle échoue

- **Statut** : Accepted — 2026-10-20 (proposée le 2026-09-16 ; phase 1 lancée par jul6art) · Livré le 2026-10-20
- **Décideurs** : jul6art
- **Specs** : § 3.1 (module Gate), § 5.1 (étape 3), § 9 (phase 1), § 13 (Gate)

## Contexte

Le constat fondateur : Claude annonce « terminé », l'humain ouvre le navigateur et trouve le défaut
(§ 1.2). La gate déplace ce moment : « tant qu'elle échoue, Claude ne peut pas déclarer le travail
terminé. L'IA se corrige **avant** que l'humain n'ouvre le navigateur » (§ 5.1).

Les assertions mécaniques issues des règles arrivent en phase 2 (ADR-0027) ; la gate de ce lot
combine ce qui existe à la fin de la phase 1, et **s'étend** ensuite sans changer d'interface.

## Décision

### Commande

```
devtools gate [--changed | --commit=<ref> | --range=<a>..<b>] [--base-url=…] [--format=text|json]
```

Étapes, dans cet ordre, **toutes exécutées** (un échec n'arrête pas les suivantes, pour que Claude
voie tout en une passe) :

| Étape | Source | Échoue si |
|---|---|---|
| `freshness` | ADR-0017 sur les workflows impactés | un workflow impacté est périmé ou non documenté |
| `scenarios` | ADR-0021 (et 0022) sur les scénarios des workflows impactés (ADR-0016) | un scénario échoue ou diffère de sa baseline |
| `verification` | ADR-0024, si un fichier impacté est un template ou un formulaire | le verdict du vérificateur est `rejected` |
| `assertions` | ADR-0027 (phase 2) — étape vide et verte avant | — |

- Workflow impacté **sans scénario** : avertissement, pas un échec (sinon la gate serait rouge sur
  tout projet qui démarre) ; `--strict` en fait un échec.
- Sortie : verdict global, puis par étape la liste **actionnable** — fichier, workflow, scénario,
  étape échouée, chemin de la capture et du diff. C'est ce texte que Claude reçoit.
- `.devtools/gate/last.xml` (ignoré par git) : dernier résultat, lu par la rétrospective (ADR-0029).

### Hook `Stop`

`claude:hook Stop` (ADR-0019) lance `devtools gate --changed`. Échec → la réponse du hook **bloque la
fin de tâche** et renvoie la sortie de la gate comme raison. Succès → rien.

- **Garde anti-boucle** : après N échecs consécutifs identiques (même empreinte de résultat, N=3 par
  défaut), le hook laisse Claude s'arrêter en exigeant qu'il rapporte l'échec à l'humain. Une gate qui
  bloque sans fin ne corrige rien.
- Aucun fichier modifié depuis le dernier succès → pas de relance.

### Précisions à l'acceptation (2026-10-20)

- **Sans source**, `devtools gate` juge l'arbre de travail (`--changed`) ; fichiers, `--commit` et `--range`
  se prennent comme pour `workflows:impact` (une source, jamais deux). Les zones de travail de DevTools
  (`.devtools/gate/`, `runs/`, `pending/`, `reports/`) ne font jamais partie d'un changement.
- **`freshness`** relance l'analyse de `workflows:check` (projet entier, sans écrire) et n'en retient que les
  workflows atteints, plus ceux que le changement déclare (une route ajoutée n'est encore sur aucune carte) :
  fait changé, point d'entrée nouveau ou disparu → échec ; code changé sans fait → avertissement. ⚠️ Cette
  étape coûte l'analyse d'un `check`, proportionnelle au projet et non à l'impact : la restreindre à
  l'extraction des seuls workflows atteints est hors périmètre.
- **`scenarios`** rejoue par le même moteur que `scenarios:run` (une `ScenarioSession` commune) et écrit son
  `result.xml`. Panther absent, pas d'URL de base : avertissement (`--strict` : échec). Une ligne par scénario
  rouge : identifiant, étape, raison, capture, image de diff.
- **`verification`** concerne un changement dont un fichier est un template (`templates/`, `.twig`) ou un
  formulaire (`Form/`). Le dossier est préparé une fois par **état** du changement (empreinte des fichiers et
  de leur contenu, attribut `fingerprint` du manifeste) ; tant que son verdict collecté n'est pas `approved`,
  l'étape échoue et dit quoi faire — `rejected` liste les constats bloquants, `inconclusive` ses raisons.
- **`assertions`** existe, verte, vide : `GateStepInterface` accueillera l'ADR-0027 sans changer la gate. Une
  étape qui lève une exception échoue avec son message ; les autres s'exécutent.
- **`.devtools/gate/last.xml`** (`gate.xsd`, ignoré par git — `init` l'ajoute au `.gitignore`) : le verdict,
  l'empreinte du changement, celle de l'échec, et le nombre d'échecs identiques d'affilée.
- **Hook `Stop`** : installé par `claude:install --hooks` avec un délai de 600 s. Rien de changé, ou succès
  déjà obtenu sur le même état : silence. Échec : `decision: block`, la sortie de la gate en raison. Au
  troisième échec identique, il bloque encore une fois en demandant d'arrêter de corriger et de rendre compte
  à l'humain ; au quatrième, il laisse finir (`systemMessage`). Projet non inspecté ou hors git : silence.

## Budget d'exécution

Proportionnel à **l'impact**, jamais au projet : seuls les scénarios des workflows impactés sont
rejoués. Temps affiché par étape.

## Hors périmètre

Assertions mécaniques (ADR-0027) ; gate en CI distincte de `workflows:check` + suite de scénarios
(déjà composables) ; parallélisation des scénarios.

## Critères d'acceptation

- [x] Modification d'un template dans `symfony-minimal` (dépôt temporaire) : `freshness`,
      `scenarios`, `verification` sélectionnés sur les seuls workflows impactés *(`route.order.new` seul)*
- [x] Un scénario cassé → gate rouge, sortie qui nomme le scénario, l'étape, la capture *(dans Chrome,
      contre symfony-minimal servi ; ignoré sans `vendor/` de la fixture)*
- [x] Toutes les étapes s'exécutent malgré un premier échec *(y compris une étape qui lève une exception)*
- [x] Workflow sans scénario : avertissement ; `--strict` : échec
- [x] Hook `Stop` : bloque sur échec avec la sortie en raison ; laisse passer sur succès *(et ne relance pas
      sur un état déjà vert)*
- [x] Trois échecs identiques → arrêt autorisé avec consigne de rapport (fixture d'entrée hook)
      *(`tests/Fixtures/claude/hooks/stop.json` ; consigne au troisième, arrêt au quatrième)*
- [x] README : section « La gate » *(« The gate »)*

## Conséquences

- Une tâche livrée par Claude a rejoué ses scénarios : ce que l'humain voit ensuite, c'est ce qu'aucun
  scénario ni aucune règle ne couvre encore — exactement ce que la phase 2 transforme en règle.
